2026-10-18, Stitch 프로젝트("문서 기반 맞춤형 홈페이지")의 5개 추가 시안 화면(Home/
Specialists/Portfolio/Programs·Pricing/Contact)을 실제 HTML 5개 페이지로 분리 구현하는
작업([[feedback_hard-rule-conflict-ask-first]] 참고 — 이 분리 자체는 AskUserQuestion으로
사용자 승인받은 아키텍처 예외)에서, 6개 화면 중 2개(Home, 초기 화면)만 전체 HTML을
`WebFetch`로 읽고 나머지 4개(Specialists/Portfolio/Programs/Contact)는 흐릿한 저해상도
썸네일 스크린샷만 보고 구현했다. 결과물은 그 4개 화면 모두 실제 시안보다 훨씬 단순했다
(통계/지표 카운터, 필터 탭, 멀티스텝 예약폼, FAQ 아코디언, 전담 스태프 그리드, 임상
케이스 스터디, 프로세스 가이드, 공지/정책 카드 등이 전부 누락). 사용자가 실제 시안
스크린샷을 첨부하며 "이것과 시안이 많이 다른데?"라고 직접 지적한 뒤에야 인지했다.

**Why**: 썸네일은 레이아웃의 대략적인 블록 배치만 보여줄 뿐 텍스트 위계, 반복 컴포넌트
개수, 세부 섹션 구성을 거의 알려주지 않는다. "화면이 몇 개 있는지"와 "각 화면에 실제로
무엇이 들어있는지"는 전혀 다른 정보이며, 전자만 보고 후자를 추측하면 필연적으로
과소구현하게 된다.

**How to apply**: Stitch(또는 유사 디자인 도구) 프로젝트에서 여러 화면을 구현해야 할 때는
작업을 시작하기 전에 **모든 대상 화면의 전체 HTML 소스를 먼저 가져와 읽는다** — 화면
개수가 많다고 일부만 썸네일로 때우지 않는다. 각 화면의 실제 소스를 다 읽은 뒤에야
공통 패턴(어떤 content.json 필드를 재사용할 수 있는지, 어떤 render 함수를 재사용할
수 있는지)을 파악하고 구현에 들어간다. 이 저장소처럼 "실사진 금지"·"브랜드명 고정"·
"가짜 통계 금지" 같은 하드 규칙이 있는 프로젝트에서는, 원본 Stitch 마크업의 과장된
수치(예: "1,840+ cases", "99.4%")나 실사진은 그대로 베끼지 않고 데이터 기반의 솔직한
값(실제 `beforeAfter`/`reviewGallery` 개수 등)으로 대체해야 한다는 점도 같이 적용한다.
