2026-09-09, `.inquiry-fab`(우측 스크롤바 퀵 탭) 검증 작업 중 실제로 벌어진 일: 작업 지시문은
"방금 바꾼 상태"를 다크 배경(#1B1608) + `.inquiry-fab__label`("창업 문의")과
`.inquiry-fab__sub`("QUICK CONTACT") 두 span 구조로 설명했지만, 검증을 시작해 `style.css`를
다시 읽어보니 이미 세 번째 버전(골드 `wordmarkShine` 애니메이션 그라디언트 배경 + 서브라벨
완전 제거, `.inquiry-fab__label` 하나만 남음)으로 넘어가 있었다. 시스템 리마인더도
"index.html was modified... by the user or by a linter"라고 알려왔다 — 세션 도중 파일이
계속 바뀌고 있었다는 신호.

**Why:** 서브에이전트가 받는 작업 지시문은 호출 시점의 스냅샷이다. 사용자가 CLI에서 같은 파일을
연달아 여러 번 고치는 동안(예: 원형 FAB → 다크 세로 탭 → 골드 시머 탭) 지시문 작성과 검증 실행
사이에 시간차가 생기면, 지시문이 묘사하는 "현재"가 이미 과거가 되어 있을 수 있다. 이걸 모르고
캡처를 미리 만들어둔 사본(`_debug_*.html`)이나 초반에 읽은 CSS 내용을 그대로 믿으면 존재하지도
않는 상태(예: 검정 배경 + QUICK CONTACT)를 "확인함"이라고 잘못 보고하게 된다.

**How to apply:** 검증을 시작하기 전에 관련 CSS/HTML 셀렉터를 grep/Read로 **다시** 읽어
지시문 속 설명과 실제 파일 내용이 일치하는지부터 대조한다. 스크린샷을 여러 장 순차로 찍는
긴 검증 세션에서는 마지막에 한 번 더 같은 셀렉터를 grep 해서 중간에 파일이 바뀌지 않았는지
확인하고, 바뀌었다면 지시문의 낡은 설명이 아니라 **최종적으로 디스크에 있는 상태**를 기준으로
보고한다. `cp index.html _debug_*.html` 로 만든 사본은 그 시점의 스냅샷일 뿐이므로, 사본 기반
결과와 라이브 파일 기반 결과가 다르면 라이브 쪽을 신뢰한다.

**추가 사례 (같은 날, 같은 `.inquiry-fab`):** `getBoundingClientRect()` probe 로
`width:41 height:158`(세로로 글자가 쪼개져 쌓인 듯한 비정상 크기)를 두 번 연속 관측해
[[headless-min-viewport-width-500px]] 클램프 버그인가 의심했다. 하지만 `--window-size=500`
(클램프 임계값 밖이라 신뢰 가능한 폭)으로도 같은 수치가 재현돼 "500px 클램프 때문"이라는
가설은 틀렸음을 확인 — 실제 원인은 그 사이에 `style.css`가 또 실시간으로 수정되고 있던 것.
파일 mtime이 변하지 않을 때까지(예: 15초 간격으로 `stat -f "%Sm"` 재확인) 기다린 뒤 다시
측정하니 정상 수치(가로 폭 안에 온전히 들어오는 세로 탭)가 나왔다. **교훈:** 헤드리스 측정치가
이상하면 먼저 "알려진 헤드리스 한계"부터 의심하기 쉽지만, 이 프로젝트처럼 다른 세션이 같은
파일을 동시에 고치고 있을 가능성이 있다면 `stat` 으로 mtime 안정화부터 확인하는 게 더 싸고
확실한 첫 번째 체크다.
