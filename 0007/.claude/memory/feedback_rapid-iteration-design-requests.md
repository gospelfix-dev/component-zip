2026-09-09, 우측 스크롤바 문의 퀵 탭(`.inquiry-fab`, [[gopumgyeok-design-system]] 참고)이
한 세션 안에서 다섯 번 다시 디자인됐다: 원형 플로팅 버튼 → 다크 세로 탭(QUICK CONTACT
서브라벨 포함) → 골드 그라디언트 + `wordmarkIntro` 팝 인트로 → 골드 그라디언트 +
`wordmarkShine` 흐름 반짝임 → 애니메이션 전혀 없는 단색 골드 배경. 각 요청은 "이거 빼고
저거 넣어줘", "wordmarkIntro 이거 빼고, wordmarkShine 이거 넣어줘" 같은 한두 문장짜리
지시였고, 사이에 확인 질문 없이 즉시 반영했다.

여기서 확인된 세 가지 패턴:

1. **사용자는 이 코드베이스의 기존 keyframe/클래스 이름을 정확히 지칭해서 요청한다**
   ("wordmarkIntro", "wordmarkShine"). 처음부터 새로 만들지 말고, 요청에 등장한 이름을
   먼저 `assets/css/animations.css`/`style.css`에서 grep해 기존 정의와 사용처를 확인한 뒤
   그대로 재사용하는 것이 맞다 — 실제로 `wordmarkShine`은 `.hero-wordmark`가 쓰던 것을
   그대로 가져다 썼다.
2. **화려한 옵션(팝 인트로, 흐르는 반짝임)을 순서대로 시도해보다가, 결국 애니메이션 없는
   가장 단순한 정적 버전으로 수렴했다.** "눈에 띄게 해달라"는 모호한 요청을 받으면 처음부터
   최대치로 화려하게 만들기보다, 절제된 기본안을 먼저 제시하고 사용자가 더 화려하게 요청하면
   그때 강화하는 편이 재작업을 줄일 수 있다.
3. **각 반복마다 풀 스크린샷-검증 에이전트를 새로 띄우는 것은 비용 대비 효율이 낮다.**
   해당 세션에서 같은 요소에 대해 screenshot-verifier 에이전트를 4번 연속으로 띄웠는데,
   매번 [[gopumgyeok-headless-verification]]에 새로 추가된 "검증 도중 파일이 실시간으로
   바뀐다" 함정을 독립적으로 재발견하며 시간을 소모했다. 마지막의 단순한 변경(애니메이션
   제거 + 배경색 하드코딩 교체)은 에이전트를 띄우지 않고 코드 확인(`grep`)만으로 충분히
   검증했다 — 이 판단이 맞았다.

**Why:** 사용자는 시안 재현 정확도를 중시하지만, 이 프로젝트에서는 확정 전까지 여러 시안을
빠르게 실험해보는 방식으로 일한다. 매 반복마다 무겁게 검증하면 사용자의 반복 속도를
못 따라가고, 오래된 지시문 기준으로 보고하는 오류(라이브 파일 수정 중 스냅샷 불일치)가
반복해서 발생한다.

**How to apply:** 같은 요소를 대상으로 사용자가 짧은 간격으로 재요청을 보내는 패턴이
보이면(예: 5분 안에 3번 이상), 구조적으로 위험한 변경(레이아웃 재구성, 신규 인터랙션 최초
구현)에만 풀 스크린샷 검증을 예약하고, 색상/애니메이션 유무처럼 국소적인 CSS 값 변경은
코드 읽기로 갈음한다. 요청에 코드베이스 식별자(키프레임 이름 등)가 등장하면 먼저 grep해서
기존 정의를 찾아 재사용할 것 — 새로 만들지 않는다.
